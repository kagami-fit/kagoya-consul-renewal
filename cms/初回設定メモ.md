# KAGOYAサイト更新｜制作用の初回設定メモ

このファイルは制作担当者向けです。日常の更新担当者は操作しません。

## 一度だけ行う設定

1. 制作担当のGoogleアカウントで`clasp login`を行う。
2. `cms/gas`を対象Googleスプレッドシートに紐づくApps Scriptへ同期する。
   - `.clasp.example.json`を参考に、実際のScript IDを`.clasp.json`へ設定する。
   - `clasp push`でコードを送る。
3. Webアプリを`自分として実行`・`全員`でデプロイする。
4. シート上で`初期設定・公開データを作る`と`安全テストを実行する`を実行する。
5. Apps Scriptエディタから`getCmsDeploymentInfo()`を実行し、WebアプリURLとコールバックトークンを制作担当だけが確認する。トークンはチャット・公開ファイル・Gitへ貼らない。
6. GitHub ActionsのRepository Secretsへ次を登録する。
   - `KAGOYA_CMS_FEED_URL`：WebアプリURL
   - `KAGOYA_CMS_CALLBACK_URL`：同じWebアプリURL
   - `KAGOYA_CMS_CALLBACK_TOKEN`：Apps Scriptが生成したコールバック用トークン
7. `Publish KAGOYA CMS updates`を手動実行し、JSON更新・コミット・シート履歴の記録を確認する。

## デプロイ前のローカル試験

```bash
node cms/tests/run-local-tests.mjs
node --check assets/js/site.js
node --check cms/scripts/sync-from-feed.mjs
```

合格後、ローカルサーバーで`for-sale.html`、`index.html`、`animation-dynamic.html`を開き、販売中・成約実績・詳細リンク・画像を確認する。

## 初回の実データ試験

1. 本番に影響しないテスト行を`02_Today`へ下書きで追加する。
2. 下書きのままでは公開データへ入らないことを確認する。
3. `確認待ち`へ変更し、①入力確認→②公開申請を実行する。
4. `90_公開キュー`が`待機中`になったことを確認する。
5. ③サイト反映を実行し、GitHub Actions完了後にサイト表示と`99_更新履歴`を確認する。
6. テスト行を`非公開`へ変更し、同じ手順でサイトから消えることを確認する。

## 更新時の確認

- Apps Scriptを直した場合：`clasp push`後に新しいバージョンで再デプロイする。
- シート列を追加・削除した場合：`Config.js`と`Publisher.js`の列定義を同時に更新する。
- 公開JSONの形式を変えた場合：`schema/feed.schema.json`と`sync-from-feed.mjs`を同時に更新する。
- GitHub Actionsが失敗した場合：Actionsの実行ログと`90_公開キュー`を確認する。

## 復旧

- サイトデータはGitHubの`data/`履歴から直前の状態へ戻せる。
- スプレッドシートはGoogle Driveの変更履歴から戻せる。
- `98_公開データ`は公開済みの正本なので、直接編集しない。
